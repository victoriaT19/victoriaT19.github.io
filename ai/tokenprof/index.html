Why I built it

Agents are usually judged by one number: how many tasks they solve. I wanted to understand why an agent fails and where its context window goes, the way a profiler explains a slow program. I also wanted to learn how to evaluate agents properly when you cannot afford many runs: with a weekly GPU quota, a change that moves the score by two tasks can be pure noise.

The Gemma 4 Developer Agent competition gave me a concrete setting: small Gemma 4 models (E2B and E4B) fixing real issues in Python repositories, with a 32k-token window where every wasted token pushes out code the model needs.

What I built

  • A logging proxy that sits between any agent and an OpenAI-compatible API and records tokens, cached tokens, cost and latency for every call.
  • A trajectory profiler (tokenprof swe) that rebuilds every prompt from the competition's traces: system prompt, task, history, each tool's outputs. Tool schemas never appear in the traces, so their size is fitted by least squares from the first call of each task (1,011 tokens).
  • Twelve detectors for wasteful or failing behaviour: blind truncated file reads, repeated reads, failed edits, repetition loops that hit the output cap, context overflows, calls after submitting.
  • A Kaggle runner and paired statistical tests: McNemar for solved tasks, Fisher's exact test for behaviour.

What the profile showed

On all 129 public tasks, the official sample configuration solved 10 tasks with E4B and 6 with E2B. The profile explained much of why:

  • About 40% of prompt tokens were the same prefix (system prompt, tool schemas, task) resent on every call.
  • In 83% of E4B runs the agent read a long file without a line range and got only its first 150 lines, usually imports.
  • The edit tool failed 38% (E4B) to 70% (E2B) of the time, mostly because the model mixed lines it had seen with lines it never read.
  • The sample reserved 16,384 of the 32k tokens for output; any prompt above that was rejected, which ended 29% of E2B runs.

Fisher's exact test against the base run: * p < 0.05, ** p < 0.01. Every change moved the behaviour it targeted; none changed the number of solved tasks significantly (McNemar p ≥ 0.73). An unchanged re-run of the base solved 9 tasks and showed no significant behaviour change, so the shifts are not just run-to-run noise.

What I learned

  1. The headline metric can be blind to real improvements. With under 15 solved tasks, two more or fewer is noise. Behaviour measured over hundreds of tool calls in the same traces can be tested even when the score cannot.
  2. Always run a noise control. Re-running the baseline unchanged was the cheapest experiment and the one that made every other result believable.
  3. Small models fail at the interface, not at reasoning. They read blindly, edit from memory and stop early. Prompt rules fixed the first and the last, but not editing: the model could find the code but not copy it exactly.
  4. Defaults hide costs. One output setting silently ended a third of the small model's runs; nobody notices without looking at the traces.
  5. Write down limitations as carefully as results. The prompt rules were written after seeing the profile of the same tasks, so their gains may be smaller on new ones. The paper says so.
